# Community release review — 2026-09-04

This candidate is a substantial reliability and usability improvement, not a certification of complete replacement for every paid print-shop platform. It is staged for evaluation and has not been deployed to production.

## What changed

- Community and self-hosting are the core product. Hosting and basic setup are the optional service. AGPL licensing remains; contribution docs no longer ask for a proprietary relicensing grant.
- Release containers require validated release inputs. Linux, macOS and Windows checks protect the review path. Contribution, governance, release, backup and rollback guidance are included.
- Guided setup links normal shop workflows, migration, email, SMS, payments, optional AI and Slack. Everyday navigation is shorter; specialist controls remain under More tools. Existing typography, colors, tables and production layouts are retained.
- Manual workflows continue with AI disabled. External agents can use a shop API key with read-only or full access. A key's read-only restriction also applies when an owner cookie is present.
- SMTP setup is simpler and says what is connected. Signed Twilio incoming messages enter Conversations once, without an automatic reply.
- Customer and order CSV imports preview before writing. The UI blocks ambiguous payment statuses, partial payments and unsupported states; changing pasted data invalidates the preview.
- Stripe checkout uses shop currency and signed server callbacks. Authorize.net Accept Hosted uses the same persisted, verified payment flow. Test payments cannot settle real invoices. Card details stay with the processor.
- Customer artwork now loads correctly from installations inside hidden parent directories, while hidden upload files remain blocked.
- A reproducible isolated Dylan demo contains only synthetic customers, quotes, invoices, jobs and artwork. The demo launcher blocks outbound application connections.

## Verification evidence

The original VPS source matched GitHub v1.34.2 across the 133 inspected source files. Production was healthy at inspection. All 28 backed-up databases passed SQLite integrity and foreign-key checks. The available archive contained all 21 referenced artwork files.

The initial migration rehearsal preserved all existing rows across 739 tables, including the control database. A second rehearsal of the final payment/setup schema covered the default shop and 26 tenant databases: **7,827 existing records in 733 tables remained unchanged**. Integrity and foreign keys passed. Rehearsals used private copies; no live database was opened for writing.

The existing 955-check suite and full HTTP end-to-end suite pass locally. Additional tests exercise the isolated demo, AI-off use, API access restrictions, migration payment-state validation, signed inbound SMS, and payment callbacks. Payment tests include forged signatures, duplicate delivery, amount/currency/shop mismatches, test mode, missing callbacks, a simulated database failure with rollback, delayed payments and voided invoices. No live charge or customer message was sent.

Desktop and phone-width setup screens were inspected in the browser. The review caught and corrected stale import previews, deep-link scrolling, and unhelpful payment-connection errors. The separate marketing-site candidate builds and passes its 32 deployment-preparation smoke checks.

## Checks still required before a public release

- Review the current GitHub candidate and its current-commit CI results; a previous green run does not certify later edits.
- Configure and verify actual provider callbacks on the public HTTPS hostname. One of the 26 backed-up active shops had a live Stripe key. It needs its new callback signing secret before this candidate starts new checkouts. No merchant credentials were copied into source or demo files.
- Complete merchant-owned Stripe and Authorize.net sandbox acceptance, including a customer closing the checkout page before returning. Local fixture tests do not prove a merchant account or public callback is configured correctly.
- Review Dylan's local evaluation copy, then provision an isolated public evaluation instance. No account invitation or demo message has been sent to Dylan.
- Obtain the explicit deployment instruction required by the workspace policy. Take a fresh backup immediately before deployment, verify rollback, deploy the reviewed commit and run production smoke checks.

## Remaining product gaps

Refunds, chargebacks and processor-side voids are not yet automatically reconciled into invoices. SMTP does not sync a mailbox into Conversations. The migration UI accepts mapped CSV customer/order history, not every proprietary CRM archive, active production state, partial-payment ledger, custom field, artwork bundle or PDF invoice. The external-agent setup supplies API access; it does not install and operate an arbitrary agent runtime for the shop. A full storefront/fundraising suite, visual product designer and general ledger remain separate work in the roadmap.

These limits are visible in the product/docs so the podcast demo can show actual working features without promising unbuilt functionality.
