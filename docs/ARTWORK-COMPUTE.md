# Artwork tools and compute ownership

Updated for the v157 browser composer, 2026-09-04. The current implementation and future adapter designs are separated below. PrintShopCRM works without AI. The free core does not depend on a paid artwork service. Artwork rendering belongs on the shop's device or its own provider account. Any future hosted processing requires separate, explicit metering and payment; it must not run inside the CRM request process.

## Current behavior

Manual proof uploads, version history, customer approvals and staff technical releases work without AI. The job now stores original artwork and prepared production files independently of the appearance proof, with private staff download routes, immutable file metadata and recorded SHA-256 digests. A manager records the selected files, reviewed dimensions, method, equipment notes and an explicit human review against the current approved proof. A release opts that job into enforcement; the additive migration leaves legacy jobs optional and does not mark old approvals technically ready. Proof, production-relevant job and file changes invalidate readiness. See [artwork and production release](ARTWORK.md) for the exact checks, API contract and storage boundary.

File signatures and hashes are checked on asset upload and selected file bytes are checked again at release. These checks are bounded file I/O, not artwork rendering, separation, stitch generation or machine validation. The server does not continuously monitor external filesystem changes after release. Prepared-file handoff is manual; it does not automatically launch a vendor tool or a RIP.

The native job composer now places original raster artwork on a manually uploaded product photo or an optional exact-SKU S&S photo. Placement, proportional scaling, rotation and PNG export run in the browser. It uses no AI, server renderer or vendor rendering API. Still PNG/JPEG/WebP inputs are limited to 10 MiB each, 4096 pixels per edge and 8 million pixels combined. PNG output is limited to 2000 pixels per edge, 4 million pixels and 16 MiB. Shared bounded header inspection precedes browser decoding, and EXIF orientation is explicit. Browser bitmaps are closed on replacement/exit; preview updates are coalesced and stale loads are discarded.

Saving uploads the original bytes unchanged as private source assets and creates a draft `appearance_mockup` proof with the placement recipe and hashes. Original assets, draft proof, approval clearing, technical hold, revision and retry receipt commit together. The current tab preserves the exact save payload after a failed or uncertain response. Exact retries return the original committed proof; editing creates a new request. There is no durable unsaved-draft recovery across a tab closure. See the [composer contract](MOCKUP-COMPOSER-CONTRACT.md) for the full lifecycle and limits.

Autopilot's optional generic garment illustration remains a separate concept and is never uploaded as a customer proof. There is no hosted rendering service, artwork-provider rendering adapter, shop worker connector, paid compute plan, PSD editor integration or built-in separation engine in this release. The implemented S&S adapter supplies photo bytes and provenance only.

## Implemented S&S photo connection

The composer accepts an exact S&S SKU, including the product's color and size variant, using the shop's S&S account number and API key. The new adapter calls S&S's product API and requires exactly that SKU in the response. It offers only returned color-specific front/back/side/direct-side or on-model views. Missing credentials, product identity or photo views leave an actionable error and the manual photo path available. No generic garment or approximate color is substituted.

The authenticated media route accepts opaque, shop-scoped handles rather than client URLs. It downloads from explicitly allowed S&S HTTPS image hosts, checks and pins public DNS addresses, refuses redirects and compressed HTTP responses, and never sends supplier credentials to image hosts. Product responses are capped at 512 KiB; image responses at 10 MiB; each supplier operation has a 12-second deadline. Supplier concurrency is four globally and two per shop, with separate bounds through outgoing image-response completion. Handles last ten minutes and have bounded count/metadata storage. Image response bytes are not cached for later requests.

The returned signed ticket binds the shop, SKU/style/brand/color/size/view, source URL, SHA-256 digest, retrieval time and one-hour expiry. Saving verifies that ticket against the original photo bytes, then records the stable supplier identity and digest in the canonical recipe. A ticket failure cannot become a verified photo. The user may explicitly keep it as an unverified shop photo. The saved recipe is provenance evidence, not a claim about calibration, image licensing or a manufacturer's production approval.

This connection uses the [S&S product API](https://api.ssactivewear.com/V2/Products.aspx). It does not implement the [S&S PromoStandards Media Content service](https://promostandards.ssactivewear.com/), SanMar media or a third-party renderer's SKU-to-template mapping. [SanMar integration offerings](https://info.sanmar.com/resources/electronicintegration/integrationofferings) remain a future adapter reference; the current composer does not expose SanMar photo lookup. Supplier account availability, image rights and real provider responses still require the shop's own setup and review.

The current composer is deliberately visual. Requested physical dimensions are notes; they do not calibrate the photograph, enforce printable areas or generate production artwork. Future calibrated templates need explicit print-area definitions, supported transforms and distribution rights. PSD editing remains optional: if an embedded editor is added, validate message origin and source window, serialize requests and bound binary inputs/outputs. Keep native placement and ordinary uploads available without that editor.

## Execution and billing boundaries to implement

1. **Browser:** The native compositor already runs on the device with bounded input/output sizes and load cleanup. It does not use a rendering worker or offer a GPU service. Future heavier tools need their own memory/runtime controls and a worker where supported. An underpowered phone can use a shop computer; there is no silent server-render fallback.
2. **Shop worker:** Pair a revocable, tenant-scoped worker. It pulls jobs outbound over HTTPS; no public GPU port or exposed LAN endpoint. Lease each task, heartbeat, hash inputs/outputs and reject expired or superseded results. Permit only supported workflow versions and typed parameters, not arbitrary scripts or ComfyUI custom nodes from a job request.
3. **Shop provider account:** Show the provider and payer before submission. Separate artwork-provider credentials from the agent's model credentials. A shop's chat-model subscription does not imply access to any image API. Apply per-shop concurrency and spending caps; reconcile uncertain provider submissions before retrying so a timeout cannot repeatedly spend money. An unavailable provider leaves a retryable draft.
4. **Optional hosted compute:** Disabled until configured by the operator and explicitly enabled by the shop. Use separate workers and queues with CPU/GPU, memory, runtime, pixels, storage and concurrency ceilings. Reserve budget atomically before dispatch, use idempotent requests and durable usage records, reconcile provider charges, and refund unused reservations. Show estimated cost and hard caps; never bill an automatic retry twice. No unlimited processing bundled into basic CRM hosting.

The shop-worker, provider-spending and hosted-compute controls above are requirements for future adapters, not installed services or an existing paid compute offering. The manual CRM core and native composer remain usable without AI or a paid artwork connector. Future rendering should use the shop's browser/hardware or its own provider account; hosted processing must be a separately priced, explicitly enabled option with the caps and metering above. No silent fallback may move a local/BYO job onto the CRM operator's compute bill.

Ordinary file storage, network transfer and bounded validation still consume server resources; local rendering does not make hosting cost-free. The current per-file and per-job asset count limits are not a complete storage quota, retention policy or hosting billing system. Those hosting controls still need implementation before promising unlimited community or hosted storage.

## Production acceptance

Customer appearance approval and staff technical release are now separate records. An attractive mockup is not separation, digitizing or machine validation. Attach reviewed separation files and record screen count, inks, print size, underbase, mesh/LPI/angles and RIP profile in the appropriate review fields/notes. Preserve original vectors and spot channels. An embroidery texture effect is not a stitch file, and the technical release does not claim that the CRM verified a sew-out or decoded the stitch path.

Before promoting an adapter, test it against real shop fixtures: front/back of the correct tee and hoodie, dark/light garments, fine text, transparency, spot colors, gradients, large files, limited-memory devices and provider failures. Compare exported dimensions/channels and run a physical test print or RIP check where applicable. Automated digitizing remains out of scope until stitch output can be independently verified; importing a professionally prepared file remains useful.

Implemented: separate source/prepared-file handoff, appearance approvals, explicit staff technical release, native browser photo composition and optional exact-SKU S&S photo retrieval. Next work: richer source preflight and calibrated templates; optional PSD editing; shop-owned worker/provider adapters; separately metered hosted compute last. No paid connector should gate quoting, proofs, production, invoicing or other manual workflows.
