# Bring existing records

Use Setup & connections → Import data. CSV is the supported interchange format for customer lists and historical orders. Keep original files and a backup, and preview a small representative sample first. Export templates and field names vary between CRM versions: this is a column-based importer, not a native API migration from every vendor.

Customer headers: name, email, phone, company, notes, tags, billing and shipping address, tax exempt, resale number, payment terms. Tax-exempt status (yes/true/1/exempt), the resale number and Net 15/30/45 or Due on receipt are carried onto the customer; a term the app has no equivalent for (Net 60) keeps the default rather than a guess, and a resale number alone marks the customer exempt unless the file says otherwise. First/last name variants and many common vendor headers are recognized. Duplicate customers are skipped by email; rows without email require review before rerunning. Customer import never updates existing records. A row whose email or phone holds more than one address ("a@x.com, b@y.com") is refused and listed under `rejected` with the reason — one address per customer, as on the customer form.

Order headers: customer, email, invoice #, date, status, product, qty, unit price, subtotal, sales tax, total, amount paid, balance, PO number, job name/nickname, customer due date, payment due date, notes. Use ISO dates (YYYY-MM-DD). Common synonyms and apparel size columns are recognized, and snake_case headings (`order_number`, `grand_total`) are read the same as spaced ones. Sales tax is stored as tax (with the rate it works out to), not folded into a line. The PO number lands on the invoice, the job name on the job, the customer due date on the job and the payment due date on the invoice. A line with a quantity and no size columns stays a plain quantity. A file in which no column is recognised as a customer, an order number or a total is refused (`import_unmapped`) instead of importing blank records.

Amount paid and balance decide payment in both modes: paid in full, part-paid (one `imported` payment row for the amount collected, balance left open in A/R) or unpaid. Imported payments are history — they send no receipt and fire no automation or webhook. The preview groups repeated order numbers and shows totals before writing.

The current UI uses `status_policy: strict`. Explicit paid, unpaid, and quote states are accepted. Blank/unknown states, production completion without a payment state, and partial payments pause the whole import — unless the file's Amount paid or Balance column is mapped, in which case the amounts decide. Historical invoice jobs are marked complete; active production and arbitrary workflow states need a separate migration. Do not relabel an uncertain payment merely to pass validation.

Direct legacy API calls without status_policy keep a lenient reading, with limits (tightened in 1.39): explicit settled words (paid, settled, payment received) are imported as paid history, and so is every row of a file that has **no status column at all**; open, due, pending, invoiced, not paid and an approved/accepted order (“Quote Approved”) are imported unpaid; cancelled, voided and refunded orders are skipped (counted as `skipped_cancelled`). Production words (complete, delivered, shipped, closed), “partial”, a blank cell in a file that does have a status column, and any other status stop the import and are named in the error — unless an amount-paid or balance column settles them. Before 1.39 those were read as paid in full (or, for “partial”, as unpaid with nothing received). In both modes cancelled/voided/refunded orders are skipped, a quantity above 1,000,000 pieces stops the import, and imported lines are priced at the file's own unit price — today's extended-size upcharges are never added to historical lines. New integrations should always send status_policy=strict.

Review totals and original invoice references after import. Repeating the exact same order export skips existing source references. If a source lacks order IDs, keep the exact original file for retries; re-exporting can change the fallback identity. PDFs, artwork, custom objects, mailbox archives and vendor-specific attachments are not imported by these CSV tools.

The preview is invalidated when pasted data changes, inputs stay locked while a request runs, and repeated clicks cannot submit competing imports from the same dialog. Failed batch imports report already-written counts rather than pretending nothing was saved.
