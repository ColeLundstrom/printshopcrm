# Core workflow readiness

Reviewed September 4, 2026. PrintShopCRM is free AGPL software with an optional hosting/setup service. A shop can operate it manually with AI disabled. This checklist describes the current candidate; it does **not** claim complete Printavo parity or certify every shop’s provider configuration.

**Implemented** means code and local/isolated regression coverage exist. **Partial** means a useful workflow exists with a material limit. **Missing** means there is no supported workflow yet. **Needs provider acceptance** means the adapter still needs testing with the shop’s own account and public HTTPS callbacks. A fixture passing is not evidence that a live provider is configured correctly. Release readiness also requires CI against the exact commit being installed.

## Available workflows and their limits

| Area | Status | What to expect |
|---|---|---|
| Manual operation | Implemented | Customers, quoting, invoices, tasks, production and recordkeeping work without a model key. Email, SMS and online payments need their own connections. |
| Customers and documents | Implemented | Customer history, CSV import/export, billing/shipping postal text, estimates, invoices, fees, discounts, taxes, payments and PDFs. Documents save their own addresses; changing customer defaults does not reroute existing jobs. Postal text is not carrier validation. |
| Quote approval and repeat orders | Implemented | Quote terms and acceptance history are recorded. Commercial changes supersede approval and require a new customer link. Repeat work creates a new quote; it does not inherit a prior order’s approval, payment or production completion. Older historical terms may be unknown and are labeled accordingly. |
| Pricing and profitability | Partial | Editable/importable price matrices, decoration/contract pricing, job cost inputs, machine/member rates and recorded output. The quote’s quick margin preview is an estimate for supported screenprinting work. Use job costing for other methods and actual expenses; configured rates and recorded time/output determine the usefulness of the result. |
| Production organization | Implemented | Reusable workflows, combined project types, task assignments, department queues, optional timing, calendar views, receiving counts, QC steps and optional staff-authenticated QR handoffs. Timing may be disabled. Payment and production due dates are separate when converting a quote. |
| Purchasing and receiving | Partial | Reviewable PO details, explicit manual supplier-confirmation records, partial receipts, corrections and manager short-close. A prepared PO does not mean an order was placed. Automatic submission requires exact supplier item identifiers and confirmation; ordinary catalog-style POs currently require manual ordering. Damaged-goods issue/resolution tracking is still missing. |
| Catalog connections | Needs provider acceptance | S&S catalog/media and configured supplier pricing/status/package reads, including supported PromoStandards calls. Credentials, service versions, exact SKU/color/size matching and account permissions must be checked. SanMar electronic PO submission is not implemented. See [connections](CONNECTIONS.md). |
| Artwork and mockups | Implemented, bounded | Versioned customer appearance proofs, browser-only manual photo/raster mockups, private originals/prepared production files, and a separate staff technical-release review. Visual approval does not certify production files. No automatic digitizing, machine/RIP validation or production separation engine is provided. See [artwork](ARTWORK.md). |
| Artwork compute | Partial | Current manual browser composition uses the operator’s browser. No hosted heavy-compute service or AI mockup/separation provider adapter is built. Future local/BYO-account processing and separately priced, capped hosted opt-in are design constraints, not available services. See [compute policy](ARTWORK-COMPUTE.md). |
| Email, SMS and conversations | Partial; needs provider acceptance | Guided email/Twilio setup, outgoing messages, supported inbound callbacks and customer conversation history. SMTP alone does not synchronize an email mailbox. Unsent conversation drafts stay with their customer in the current browser session; a page reload can lose them. Separate billing recipients are not yet modeled. |
| Payments and accounting | Needs provider acceptance | Stripe and Authorize.net hosted checkout adapters, verified payment recording, deposits/manual payments, refund/void reconciliation, explicit credits and A/R reporting. Refunds are initiated in the processor dashboard. Other processors can be recorded manually. Chargebacks/unmatched payments and QuickBooks credit/refund documents require separate reconciliation. See [payments](PAYMENTS.md). |
| Optional AI and Slack | Partial; needs provider acceptance | BYO model configuration, scoped external-agent API access and supported Slack shop-assistant tools. Connecting an arbitrary agent does not install or operate its runtime. Provider costs, permissions and allowed actions need account-specific review. See [Slack setup](SLACK-SHOP-ASSISTANT.md). |
| Migration and branding | Implemented with limits | Mapped CSV customer/order-history import with preview, editable shop logo/colors, and data exports. Proprietary archives, complete active workflow state, partial-payment ledgers and artwork bundles are not universally imported. See [migration](MIGRATION.md) and [branding](SHOP-BRANDING.md). |
| Community and self-hosting | Implemented | Source/license access, contribution/security guidance, automated checks, backup/migration/release tooling, and optional project support. Hosting pays for operating/setup help; it does not unlock the software. These safeguards reduce risk and do not guarantee every change is regression-free. |

## Priority gaps before claiming broad replacement

1. **Capacity accuracy.** The current Capacity planner uses a shared screenprinting model for active jobs. Its promise dates must not be treated as a complete embroidery/DTF/machine schedule. First expose unsupported work clearly; then add method-specific machine availability. Printavo’s comparable station/work-type scheduler is [Power Scheduler, Premium](https://support.printavo.com/hc/en-us/articles/46724003227035-4-8-Power-Scheduler-Premium).
2. **Billing recipients.** A school buyer and its bookkeeper need separate message destinations without changing the main customer email. Printavo documents a [designated billing contact](https://support.printavo.com/hc/en-us/articles/46723960419099-3-3a-Billing-Contact).
3. **One shipping record across views.** Department shipment history and Sales → Orders tracking currently use separate records. Carrier label purchasing is absent. Consolidate multiple parcels/pickups before adding an own-account label adapter. Printavo’s [shipping workflow](https://support.printavo.com/hc/en-us/articles/46723948276123-Shipping) includes EasyPost labels on Standard+.
4. **Reusable payment terms and delivery defaults.** Explicit dates work, but customer-specific Net 30/due-on-receipt and ship/pickup defaults are not structured fields. See Printavo’s [dates, delivery and payment terms](https://support.printavo.com/hc/en-us/articles/46723957503387-3-4a-Dates-Delivery-Method-and-Payment-Terms).
5. **Receiving exceptions.** Partial counts work; damaged/rejected blanks need their own auditable issue and resolution instead of relying on notes and shortages. See Printavo’s [receiving workflow](https://support.printavo.com/hc/en-us/articles/46723949309723-3-10-Receiving), a Premium feature.

Printavo’s [current pricing](https://www.printavo.com/pricing/) separates these tiers. Storefront/fundraising products, native mobile apps, full accounting and digitizing are additional scope, not evidence that the ordinary manual workflow is absent here.

## Acceptance before a public demonstration or upgrade

Use synthetic data to run a complete order: returning customer → mixed garments/sizes and pricing → approval/revision → deposit → PO confirmation → partial receiving → assigned production/QC → packing/shipping → final payment → reorder. Reopen it after a restart and reconcile quantities, money, dates, addresses, files and history. Inspect the phone workflow and printed documents.

Run current-commit tests and migration rehearsals, retain a verified backup/rollback path, and complete provider-owned sandbox acceptance on the intended HTTPS hostname. The isolated demo blocks outbound application connections and is not a substitute for those provider checks. Never describe a local sample as a publicly reachable deployment until that instance has been verified.
